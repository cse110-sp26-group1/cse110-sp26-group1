# Semantic Versioning
This document explains how semantic versioning was incorporated in our project.

Semantic versioning is carried out automatically using GitHub Actions; however, we also manually update versions if they are not consistent with the changes we have made in our project. A future step is to figure out a better system for this.

Under `.github/workflows`, we have a file known as `release.yml`. This uses the npx package `semantic-release`. Whenever there's a pull request, the CI/CD pipeline gets triggered, which also checks and creates the appropriate version.

**Related files:**
`research/semantic-release/semantic-release workflow.md`

When a file is pushed to main, a new tag and release are usually generated by GitHub Actions. The contents of the release show any fixes or features that were added to our project. It does this by looking at conventional commits. For both pull request titles and commit messages, we ensure that we use conventional commits so that semantic release can detect them while creating a new tag and/or release.

The tag follows semantic versioning format, for example:

`v2.1.0`

| Digit | Meaning |
|-------|---------|
| `2` | Breaking change |
| `1` | New feature added |
| `0` | Bug fixes |

We make sure to use version-affecting tags like `feat`, `fix`, etc. (more in the semantic-release workflow file) if any changes affect the functionality of our project.

We also use non-version-affecting tags, usually for documentation or style/formatting changes to files, as they do not affect our issue-tracker functionality.
